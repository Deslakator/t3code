# Сопровождение форка T3 Code

## Репозитории и ветки

- `origin` — личный форк: `https://github.com/Deslakator/t3code.git`.
- `upstream` — репозиторий авторов: `https://github.com/pingdotgg/t3code.git`.
- `main` — чистая копия основной ветки upstream. Собственные коммиты сюда не добавляем.
- `my-product` — основная ветка форка на GitHub, для собственной версии и этой инструкции.

Основная ветка upstream определена через `git ls-remote --symref upstream HEAD`:
на момент настройки это `main`. Если авторы переименуют её, сначала проверьте
новое имя и скорректируйте команды. Обновления выполняются вручную, без расписания
и автоматического слияния. Опубликованную историю не переписываем: без rebase и force push.

## Обновление чистой ветки

Выполняйте команды из корня репозитория, по одной, проверяя результат каждой.
Перед переключением `git status --short` должен быть пустым. Незавершённую работу
сначала сохраните коммитом в своей рабочей ветке или через `git stash push -u`.

```bash
git status --short
git fetch origin
git fetch upstream
git switch main
git merge --ff-only origin/main
git merge --ff-only upstream/main
git rev-parse main upstream/main
git push origin main
```

Два SHA из `git rev-parse` должны совпадать. Если любой merge отказал или SHA
различаются, остановитесь: изучите `git log --graph --oneline --decorate --all`.
Не создавайте merge-коммит в `main`, не применяйте reset и force push для обхода
расхождения: сначала выясните происхождение лишних коммитов и сохраните их историю.

## Слияние обновлений в свою версию

После успешного обновления `main` и при чистом рабочем дереве:

```bash
git switch my-product
git merge --ff-only origin/my-product
git merge main
```

Последняя команда сохраняет собственные коммиты и при необходимости создаёт
merge-коммит. Если локальная и удалённая `my-product` разошлись, сначала изучите
изменения обеих сторон и объедините их через `git merge origin/my-product`,
затем выполните `git merge main`. Не используйте rebase опубликованных коммитов.

## Конфликты

1. Выполните `git status` и `git diff --name-only --diff-filter=U`.
2. Разберите каждый конфликт, сохранив нужные изменения своей версии и авторов;
   удалите маркеры конфликтов. Не выбирайте целиком одну сторону без проверки.
3. Добавьте каждый разрешённый файл командой `git add <путь>`.
4. Проверьте `git diff --cached`, затем завершите слияние: `git merge --continue`.
5. Установите зависимости и выполните проверки ниже до отправки ветки.

Чтобы отменить именно незавершённое слияние и вернуться к состоянию до него:

```bash
git merge --abort
```

Начинайте merge с чистым рабочим деревом, чтобы отмена не затронула несохранённую
работу. Если изменения сохранялись через stash, возвращайте их отдельно через
`git stash apply` после слияния и проверок; удаляйте stash только после проверки.

## Проверки перед публикацией

Сначала перечитайте актуальные `AGENTS.md`, `README.md`, `CONTRIBUTING.md` и
`docs/operations/development.md`: команды и требования upstream могут измениться.
Vite+ (`vp`) устанавливается способом из README и предоставляет Node,
указанный в `package.json`. Не запускайте повторную установку параллельно
работающему setup из `.t3/setup-running`.

```bash
vp i
git diff --check
vp run check:changed
git status --short --branch
git log --oneline origin/my-product..HEAD
```

`check:changed` сравнивает изменения с `origin/main` и запускает применимые
проверки формата, lint, типов и тесты. Для изменённого поведения дополнительно
запускайте сфокусированные тесты, например `vp test run <путь-к-тесту>`, и
проверяйте затронутые сценарии в нужных клиентах и режимах подключения.
Полные проверки репозитория оставляйте CI, как требует `AGENTS.md`.

Перед выпуском артефакта проверьте сборку нужной платформы по runbook
`docs/operations/development.md` и процедуру выпуска в `docs/operations/release.md`.
После push проверьте результаты доступных GitHub Actions; локальные проверки
не заменяют CI. Не публикуйте релиз при неразрешённых ошибках.

Убедитесь, что нет случайных изменений lockfile, секретов или посторонних файлов,
и что `main` по-прежнему совпадает с последним полученным `upstream/main`.
После успешных локальных проверок отправьте обновлённую ветку:

```bash
git push origin my-product
```

## Лицензии и авторские права

Сохраняйте оригинальный `LICENSE`, уведомления об авторских правах и лицензии
сторонних зависимостей, в том числе в распространяемых артефактах. При обновлении
зависимостей проверьте требуемые уведомления и предусмотренную upstream команду
`vp run licenses:sync`; изучите её изменения перед коммитом. Собственные изменения
не отменяют требований исходной лицензии и лицензий зависимостей.
